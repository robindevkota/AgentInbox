## Remaining Engine Gaps — Must Fix Before Launch

### Gap 1 — Worker spawn timeout (no timeout on Claude process)
**File:** `.agentinbox/worker.js` (generated by setup prompt in routes.ts)
**Problem:** Worker spawns Claude and waits forever for `proc.on("close")`.
If Claude hangs (MCP subprocess crash, stuck tool call, infinite loop),
`claudeRunning` stays `true` permanently — worker is dead until restarted.
The 15-min lockfile guard only covers the MCP path, not the worker's in-memory flag.
**Fix:** Kill the Claude process after 15 minutes if it hasn't exited.
**Effort:** 30 min

---

### Gap 2 — No Telegram alert when worker fails to connect
**File:** `.agentinbox/worker.js` (generated by setup prompt in routes.ts)
**Problem:** If the worker can't reach the server (network down, bad token, server restart),
it silently retries every 5 seconds and logs to `worker.log`. Developer never knows.
First symptom is "tasks not getting picked up" — looks like a product bug, causes churn.
**Fix:** After N failed connection attempts, POST to Telegram bot directly to alert developer.
**Effort:** 1 hour

---

### Gap 3 — No rate limit on submission form
**File:** `packages/server/src/api/routes.ts` — POST /submit/:token
**Problem:** Anyone with the submit token can POST unlimited tasks.
Each task wakes Claude (sequentially due to lockfile, but still).
100 tasks = Claude runs 100 times = token burn with no cap.
**Fix:** Max 10 tasks per hour per submit token. Return 429 after limit.
**Effort:** 1 hour

---

### Gap 4 — PROJECT_CWD fallback is fragile
**File:** `packages/mcp/src/index.ts` line 39
**Problem:** `const PROJECT_CWD = process.env.CLAUDE_PROJECT_PATH || process.cwd()`
If CLAUDE_PROJECT_PATH is not set (MCP path without worker), Claude edits whatever
directory the MCP process started from — could be wrong project entirely. Silent and destructive.
**Fix:** Log a clear warning on startup if CLAUDE_PROJECT_PATH is not set. Validate it exists.
**Effort:** 30 min

---

### Gap 5 — Black box between "Claude is on it" and "Done"
**Problem:** No visibility into what Claude is doing during a task.
For a 90-second task it feels broken. For a 5-minute task users think the system is down.
**Fix:** Show elapsed time + last action in PM dashboard task card while status = in_progress.
Minimum: "Claude picked up this task 43s ago."
**Effort:** 2-3 hours

### ✅ Gap 6 — No failure contract for environment errors — FIXED
**Files:** `packages/server/src/api/routes.ts` (TASK_PROMPT in setup endpoint) + `packages/mcp/src/index.ts` (TASK_PROMPT)
**Problem:** `--dangerously-skip-permissions` removes the "ask human" escape valve.
When the environment is broken, Claude has no explicit instructions — it improvises unpredictably:
- Port conflict → may loop retrying, may try random ports, may complete without screenshot
- Playwright missing → tries Python/selenium, pip install fails, loops, lockfile held 15 min
- PDF parse fails → server returns "[Could not parse file]", Claude works blind, fixes wrong thing
- npm install fails → can't start app, no screenshot, loops trying alternatives
- Any of the above → lockfile held until 15-min timeout, token burn, task never completes cleanly

**Root cause:** TASK_PROMPT gives Claude a happy path but no exit path for failures.

**Fix:** Add explicit failure contract to both TASK_PROMPT strings:
```
Environment failure rules (ALWAYS follow these):
- If app won't start (port conflict, missing dep, install fails): do NOT retry more than once.
  Call complete_task WITHOUT screenshot. Note reason in summary_technical.
- If Playwright/screenshot tool missing: skip screenshot entirely. Complete the fix, note it.
- If file attachment unreadable ("[Could not parse file]"): proceed without it, note it.
- If any tool fails twice in a row: stop trying that approach. Complete or escalate.
- NEVER loop more than 2 attempts on any single environment operation.
- NEVER let an environment issue block task completion.
```
**Effort:** 1 hour (update both TASK_PROMPTs + test)
